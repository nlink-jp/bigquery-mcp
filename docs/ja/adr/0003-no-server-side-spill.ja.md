# ADR-0003: サーバー側スピルを持たない — 明示キャップと省略の計上

| 項目 | 内容 |
|-------|-------|
| ステータス | **採択** |
| 日付 | 2026-09-06 |
| 拘束対象 | bigquery-mcp |
| 決定者 | nlink-jp maintainers |
| 契機 | RFP §2「入出力」。初稿は splunk-mcp の `workspace_root` JSONL スピルを再利用したが、保守者がフリートはその方式を廃止中と示した — 結果はレスポンスで返し、ファイル化はエージェントランタイムが行う |

## 背景

このフリートの file-mediated なサーバー 7 本が、それぞれ `workspace_root` 引数を持つに至っていた。閾値を超えると呼び出し側が指定したディレクトリへ結果を書き、パスを返す。組織のナレッジベースは診断を記録している —「大きすぎる」は呼び出し側のコンテキスト窓の性質であり、サーバーには観測できない。つまり 7 本のサーバーが、クライアントに無いガードを再実装していた。gem-agent は今その ガードを持ち（ADR-0058 の intake が大きすぎるツール結果をセッション work dir に退避し、モデルにプレビューとパスを渡す）、他のクライアントも独自の結果上限を持つ。

BigQuery の結果は無限（数百万行）で幅も広い（100 MB の行が合法）。サーバー側に何らかの上限は要るが、それは**キャップ**であって振り分けの判断ではない。

## 決定

1. **すべてレスポンスで返す。** `workspace_root` 引数は無く、本サーバーがファイルを書くことはなく、結果にパスは無い。
2. **明示キャップは 2 つ、どちらも計上する。**
   - `max_rows`: 呼び出し引数。既定は `[results] default_max_rows`（1000）、`[results] hard_max_rows`（50000）超は `invalid_arguments` で拒否。
   - `[results] max_bytes`（1 MiB）: 直列化したレスポンスのバイト予算。累積サイズが下回る間は行を追加し、初めて超える行で結果を終える。
   どちらかに当たれば `truncated: true`、原因を `truncated_by`（`max_rows` または `max_bytes`）に、`total_rows` は BigQuery 自身の件数を報告する。行を黙って落とす経路は無い。
3. **ページングはキャップで止まる。** `jobs.getQueryResults` は `max_rows` の残りで `maxResults` を抑えて呼び、`max_bytes` で切れた結果は手元のページで取得を止める。`max_bytes` の方が小さいので BigQuery の 20 MB ページ上限が拘束になることはない。
4. **キャップはモデルに告げる。** `get_usage` と切り詰めた全結果は次の手を言う: `LIMIT` か狭い `WHERE` を足す、上限まで `max_rows` を上げる、SQL で集約する。大きな結果をディスクに残すかどうかは本サーバーでなくエージェントランタイムが決める。

## 帰結

- 行整形のコード経路は 1 つ（`shape.go`）で、両キャップ・その相互作用・計上フィールドの単体テストを持つ。
- 幅広い行では `max_bytes` 1 MiB で返る行数が少なくなりうる。計上がそれを可視化し、操作者はより多くを扱えるクライアントのために予算を上げられる。
- Phase 2 の非同期 `get_results` は同じキャップのもと `offset` でページングし、全件が欲しいモデルは明示的にページを歩く。
- フリートの古いサーバーは改修まで `workspace_root` を保つ。本サーバーは最初から持たない。

## 検討した代替案

- **`workspace_root` スピル（splunk-mcp の契約）。** 保守者のフリート決定と上記のナレッジベースの診断により棄却。
- **キャップ無し**（「ランタイムが扱う」）。棄却: ガードの無いクライアントは `SELECT *` でメガバイト単位を受け取り、20 MB ページ上限は計上された切り詰めでなく上流エラーとして現れる。
- **行キャップのみ。** 棄却: 幅は無限であり、フリートは `limit: 3` の呼び出しで 162 KB の応答がクライアントに拒否された例を見ている。
- **部分結果のストリーミング**（複数 content block）。棄却: MCP のツール結果は丸ごと届く。ブロックに分けてもクライアントが保持すべき量は変わらない。
